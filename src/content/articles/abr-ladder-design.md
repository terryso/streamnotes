自适应码率（Adaptive Bitrate，ABR）是现代点播与直播分发的默认能力：服务端预先或实时转出多档清晰度，播放器再按瞬时带宽、缓冲水位与设备能力在档位之间切换。**省流量的核心往往不在「再压一档码率」，而在转码阶梯（rendition ladder）是否设计得克制、可切换、可缓存。**

> 档位越多不等于体验越好；过密的阶梯会同时浪费转码算力、对象存储与 CDN 缓存命中。

## 一、ABR 是什么：HLS / DASH 里的「多 rendition」

在 [HTTP Live Streaming（RFC 8216）](https://www.rfc-editor.org/rfc/rfc8216) 中，主播放列表（multivariant playlist）列出多条 `EXT-X-STREAM-INF`，每条对应一个 rendition（分辨率、带宽、编解码器等）。MPEG-DASH 用 Adaptation Set / Representation 表达同一思想。播放器周期性估算可用带宽，并在缓冲允许时上切、紧张时下切。

ABR 成立的前提有三点：

1. **服务端确实提供了多档可独立播放的媒体**（视频轨可独立，音频可共享或分轨）。
2. **清单里的带宽/分辨率等属性可信**，否则播放器会误判，频繁振荡切档。
3. **各档在时间线上可对齐切换**（关键帧与分片边界一致），否则会出现花屏、卡顿或静音缺口。

Apple 的 [HLS Authoring Specification](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices) 对档位声明、峰值码率、音频与字幕轨等有明确约束，是设计阶梯时最常用的权威参照之一。

## 二、转码阶梯怎么设计：从目标终端反推

先别急着填「240p / 360p / 480p / 720p / 1080p」模板，先回答：

- **主力设备**：手机竖屏、PC 横屏、智能电视？最高档是否值得做 1080p/4K？
- **带宽分布**：观众里有多少长期处于 1～3 Mbps？最低档是否必须低于某阈值才能「开得出来」？
- **业务形态**：点播可预转码、档位可稍密；直播受实时转码成本与延迟约束，档位宜少。

### 1. 分辨率与码率成对出现

每一档是「画面尺寸 + 目标平均码率 + 可接受峰值」的组合，而不是只改分辨率或只改码率。常见原则：

| 思路 | 说明 |
|---|---|
| 同分辨率不重复多档 | 同一分辨率塞两个接近码率，切换感知弱、存储加倍 |
| 码率大致按几何间距拉开 | 相邻档带宽建议有可感知差距（实践中常参考约 1.5×～2× 量级，按片源复杂度微调） |
| 最高档服务「好网好屏」 | 不要为极少数 4K 大屏无条件拉高全站默认最高档 |

编解码器会改变同一分辨率下的合理码率：H.264 基线仍广泛兼容；H.265/HEVC、AV1 在同等观感下通常可用更低码率，但要评估终端解码覆盖与授权/专利成本，**原则是「有覆盖再上，不要为省流量牺牲大量用户不可播」**。

### 2. 峰值码率与平均码率

清单里的 `BANDWIDTH`（及峰值相关字段）应反映真实峰值，避免「标得太低 → 播放器上切后立即卡顿再下切」。平均码率决定长期流量；峰值决定瞬时体验与移动网络下的切档稳定性。复杂运动、屏幕录制、游戏画面峰值更高，阶梯间距往往需要比访谈类内容更宽松。

### 3. 关键帧、GOP 与分片时长

ABR 切换几乎总是发生在关键帧（IDR）处。实践要点：

- **各档 GOP 对齐**，关键帧落在同一时间点；
- **分片时长与 GOP 匹配**（例如 2 秒分片对应约 2 秒 GOP），便于 CDN 缓存与播放器拼接；
- 分片过短会增加请求次数与开销，过长会加大切档与启播延迟——直播侧通常更偏向较短分片。

音频轨建议独立、码率稳定；视频切档时尽量复用同一音频，避免「切清晰度时声音跳变」。字幕与多音轨按规范作为独立 rendition / 媒体组声明，不要把字幕烧进每一档视频（除非有强合规烧录需求），否则存储会按档位数成倍膨胀。

## 三、直播 vs 点播：阶梯策略不同

| 维度 | 直播 | 点播 |
|---|---|---|
| 转码时机 | 实时，算力与路数敏感 | 可预转码、可按片源复杂度定制 |
| 档位数量 | 宜少（常见 3～5） | 可 4～7，仍忌无意义过密 |
| 延迟约束 | GOP/分片更短，阶梯切换要快 | 可略长 GOP 提压缩效率 |
| 失败代价 | 某档转码挂掉影响正在观看 | 可重转、可补档 |

直播还要注意：源站上行若只有一路中高码率，最低档依赖服务端转码；弱网上行场景应在采集端就做合理压制（参见推流参数实践），否则 ABR 只能在「已经糊掉的源」上下切。

## 四、省流量与体验的权衡：常见浪费点

1. **最低档过高**：弱网用户反复缓冲，或被迫长期卡在「开播失败 / 一直转圈」；流量未必少，体验先崩。把最低档降到「可流畅起播」的阈值，往往比再加一档 1080p 更划算。
2. **档位过密**：例如 720p 下相邻两档码率只差 10%～15%，用户感知几乎不变，却多一路转码与多一套分片缓存。
3. **最高档盲目堆高**：4K/高帧率只服务极少数终端时，全量转码会显著抬高存储与回源；可用「按需转高档」或「仅对选定片库启用」。
4. **忽略音频与重复封装**：多音轨、多字幕若错误地与每档视频复用打包不当，会放大对象数量；CDN 上分片时长不一致也会降低缓存命中。
5. **清单属性与真实码率不符**：导致 ABR 振荡（上下切循环），无效请求增多，流量与卡顿双升。

CDN 侧：稳定的分片命名、合理的缓存 TTL、避免无意义的 query 差异，能提高命中率，间接省回源流量。ABR 本身不替代缓存设计。

## 五、实践检查清单

发布或改版阶梯前，建议逐项核对：

1. **目标画像**：主力分辨率、可接受最低起播码率、是否需要 1080p/4K。
2. **档位表**：每档分辨率、平均码率、峰值码率、帧率、编码档次写清，相邻档有可感知差距。
3. **时间对齐**：各档关键帧与分片边界一致；直播/点播分片时长有明确选择理由。
4. **音频/字幕**：独立轨、避免每档烧录；多语言按媒体组声明。
5. **兼容性**：H.264 兜底是否保留；HEVC/AV1 是否仅作增强档。
6. **测量**：用真实弱网与好网各测启播时延、卡顿率、平均码率、切档次数；对照流量账单看「是否因振荡或过高最低档在烧钱」。
7. **文档**：主清单示例与 Authoring Spec 字段对齐，便于后续排障。

## 六、小结

ABR 让播放器在多档之间「能切」；**转码阶梯决定「切得值不值」**。克制的档位数、可信的带宽声明、对齐的关键帧与分片、独立的音频/字幕，再加上直播少档、点播按需加密度的策略，通常比盲目堆清晰度更能同时省流量与稳住体验。设计时以 Apple HLS Authoring Spec、RFC 8216 与 DASH 的公开约定为锚，用实测数据迭代，而不是一次定死一张「行业标准阶梯表」。
